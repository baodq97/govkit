## Cross-cutting conventions (decided once, applied uniformly)

- **Versioning:** URI versioning, `/v1` — recommended approach in `references/versioning.md`.
  Each bounded context is its own service with its own base path/spec (mirrors the
  domain-decompose service-per-context boundary), e.g. `https://api.rentfield.com/allocation/v1`.
- **Pagination:** offset/limit on every collection endpoint (`offset`, `limit`, response
  `pagination: { offset, limit, total, has_more }`). Default `limit=20`, max `100`.
- **Errors:** RFC 7807 (`application/problem+json`) on every 4xx/5xx — a shared `Problem` schema
  embedded per spec (specs are independently deployable services; no cross-file `$ref`).
- **Auth:** `bearerAuth` (JWT, Auth0-issued — see Identity) required on every operation except
  Asset Sync's internal sync trigger and Identity's own resolution endpoint's token validation
  path. Identity is cross-cutting: it does not own a resource collection consumed by other
  contexts' business logic, it backs the shared security scheme.
- **Building Blocks reused verbatim across specs (per context-map "Sharing levels"):** `Money`
  (amount as decimal string + ISO-4217 currency) is embedded identically in every spec that
  prices something (Pricing, Rentals, Billing, Payments) — versioned like a library, not a
  Shared Kernel.

## Right-sized, not cargo-culted

Per the context map's Core Domain Chart, only Allocation and Pricing carry a full domain model;
the other eleven are supporting/generic/reference contexts. Their API surfaces are sized to
match: plain CRUD/lookup endpoints for reference and record-keeping contexts (Catalog, Logistics,
Maintenance, Documents, Customer Accounts, Asset Sync), a thin contract surface for a
team-owned service (Billing), and minimal adapter-proxy endpoints for bought commodities
(Payments, Notifications, Identity). No aggregate machinery, HATEOAS, or event sourcing is
imposed where the domain model didn't ask for it.

## Flags carried over from the domain model (not resolved here — human decision)

- **`DepotTransferRequested` is an orphan event** (Allocation) — modelled as a webhook for
  completeness since it is part of the shipped aggregate's `domain_events`, but no consumer
  exists. See `allocation/README.md`.
- **`Quote` has no persisted identity** (Pricing) — `POST /quotes` is a computation endpoint,
  not a resource-with-id; if `Quote` becomes an entity later (open question in domain model),
  add `GET /quotes/{id}`. See `pricing/README.md`.
- **Payments↔Billing and Notifications↔Rentals links are "implied, not wired"** in the domain
  model — not modelled as inter-service calls here; each spec exposes only the capability its
  own context purpose states (`take card payments`, `send transactional email`).
- **Rentals' TODO to share Catalog's `Equipment` entity directly is explicitly NOT actioned** —
  Rentals keeps its own private equipment reference (an id + inline snapshot fields), per the
  context map's Shared Kernel warning.
