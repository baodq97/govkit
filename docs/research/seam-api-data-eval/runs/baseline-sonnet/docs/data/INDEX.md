Five of thirteen contexts carry **no schema at all** — each for a distinct, domain-model-stated

never states is the exact anti-pattern this design avoids (mirrors the API side declining to
invent endpoints for the same contexts).

## Cross-cutting policy (decided once here, applied uniformly below)

- **Tenancy: single-tenant.** RentField operates one system for its own business (depots,
  fleet, customers); the domain model never mentions a "tenant"/"organization" concept
  separating multiple client businesses on shared infrastructure — `SalesAccount` records are
  RentField's *customers*, not co-tenants of the platform. No `tenant_id`/`org_id` column is
  added anywhere. **Flagged assumption** — confirm if RentField itself is ever sold as
  multi-tenant SaaS to other rental companies.
- **Technical audit:** `created_at timestamptz NOT NULL DEFAULT now()` and
  `updated_at timestamptz NOT NULL DEFAULT now()` on every table, **default ON**.
  `created_by`/`updated_by` (the Identity/Auth0 subject id, `text`, nullable, **no FK** — Identity
  is an external bought adapter with no local table) are added on every table whose rows a human
  actor creates/edits through the API. Two exceptions, both automated-import read-models, use a
  business-relevant `last_synced_at` instead (no human actor exists to attribute the write to):
  `sales_account` (nightly CRM import) and `asset_record` (nightly ERP sync).
- **Soft delete: NOT added, by default.** The domain model's own declined "Audit /
  Activity-history" candidate states plainly there is "no legal or retention angle" for this
  system. That reasoning is reused here: no `deleted_at` column anywhere; deletes are hard
  deletes. Flagged — revisit if a regulated/retention requirement appears later (the same
  escalation condition the domain model gives for promoting Audit to a context).
- **Optimistic locking (`version`):** proposed on **`reservation` only** — the one aggregate the
  domain marks **High risk / core**, whose invariant ("the rules here change often") most
  benefits from a concurrent-write guard beyond the exclusion constraint. Not added elsewhere by
  default — **proposed, confirm**, not silently applied everywhere.
- **Business ownership** (from the domain, distinct from technical audit): `reservation.depot_id`
  (Custodian Depot), `sales_account.sales_rep_id` (SalesRep), `document.owner_user_id`
  (uploader) — three different ownership projections the domain explicitly says are **not** a
  single global `owner` (see the domain model's declined "Ownership/Permissions" context).
  Modelled as three separate, namespaced columns on three separate tables, never unified.

## Domain → schema mapping (per the skill's table)

| Domain element | Schema |
|---|---|
| Aggregate root (`Reservation`, `RentalOrder`) | A table: `reservation`, `rental_order` |
| Entity/record with no aggregate but named attributes (`DeliveryRun`, `MaintenanceRecord`, `Category`, `Depot`, `Tag`, `SalesAccount`, `AssetRecord`, `Document`) | Still a table — "no aggregate" (no invariant to protect) is a tactical-pattern verdict, not a "this has no persisted shape" verdict |
| Value object (`RentalWindow`, `Money`) | Inline columns on the owning table |
| Invariant (no-double-commit, min-1-day window) | A constraint: Postgres `EXCLUDE` (temporal overlap) / `CHECK` |
| Cross-context invariant (unit out-of-service, read from Maintenance) | **Not a DB constraint** — cross-context, enforced at the API/application layer, flagged in `allocation/README.md` |
| Domain event (`EquipmentAllocated`, `PriceQuoted`, `RentalOrderPlaced`, `DepotTransferRequested`) | **Not a table** — no outbox/event-sourcing was requested; events are messages, not state |
| Stateless calculation with no persisted entity (`Quote`) | **No table** (Pricing) |
| Model explicitly owned by another team (`Invoice`) | **No table** (Billing) |
| Generic bought commodity, empty `ubiquitous_language`, no aggregate (Payments, Identity, Notifications) | **No table** |
